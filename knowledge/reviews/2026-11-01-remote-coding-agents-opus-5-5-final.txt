## Remaining findings (none block draft status)

**F1. A contradictory scoping sentence (guide line 56).** "Keep the service scoped to the trial repositories" contradicts lines 51-52, which correctly say filesystem permissions define access. Reword it to: "Limit the pilot account's filesystem access to the trial repositories." Lines 56 and 81 are also unwrapped merged lines (cosmetic only).

**F2. Crash semantics are missing (knowledge lines 104-106 and the lifecycle table).** The text covers a normal shutdown but not a crash. If the shared Copilot child exits or its connection closes, `discardTransport` clears every active Copilot session on that host (`copilotTransport.ts:1347-1380`). Add one sentence on this, and add a lifecycle case: "Copilot child exits during a turn."

**F3. Withdrawing my plugin-injection claim.** My addendum's B5 said system-message injection "remains even then" (that is, even with `COGPIT_SKILL_HOME` set). I withdraw that.
- `withPluginSkills` (`copilotTransport.ts:111-116`) appends text only when `pluginSkillContext` returns some.
- `skillInstructions` (`server/plugins/manager.ts:175-197`) returns an empty string when:
  - plugins are unavailable or closed;
  - `COGPIT_DISABLE_PLUGINS=1` is set (line 173);
  - no plugin is enabled, error-free, host-compatible and contributes skills;
  - no plugin's scope covers the workspace.
- The bundled helper skills are a separate path that writes files into agent homes.

Knowledge lines 86-87 are worded correctly ("can separately append"), and nothing claims `COGPIT_SKILL_HOME` removes all additions. A useful extra step: record the enabled plugins and the safe-mode state before the pilot.

**F4. Mac-side rollback is only implied (guide line 142).** It should explicitly list:
- the app bundle;
- application-support data and the device registry;
- any release the updater has staged;
- the bootstrap marker directory;
- the pilot account itself, if one was created.

## Corrected assessment of the VS Code Agents window row

I checked two primary pages: agent-harnesses and remote-agent-sessions. The knowledge row (line 134) is fair but incomplete.

- **Copilot runs through an SDK, not necessarily your installed CLI.** The Copilot harness runs on the Copilot SDK inside VS Code's Agent Host. Whether it uses the server's installed Copilot CLI binary, its `~/.copilot` settings and its existing CLI session history is unknown.
- **Claude and Codex are also not the native CLIs.**
  - Claude runs on the Claude Agent SDK; the docs do not establish parity with the Claude Code CLI.
  - Codex runs either through the OpenAI extension or an experimental Agent Host integration.
  - Harness customizations, including hooks, "follow the selected harness".
- **There is a third connection path the row omits:** GitHub Environments (Preview), which reaches GitHub Mobile and GitHub.com. Add it to the row.
- **None of the three paths is Tailscale-only.**
  - GitHub Environments is mediated by a GitHub account and the cloud.
  - Dev tunnels are an authenticated relay, presumably Microsoft-hosted.
  - SSH works only from the VS Code desktop client.
  - So a private phone path is unverified, as the row already says.
- **Host-side requirements.** Sessions need the agent host running. For desktop-hosted sessions the VS Code application itself must keep running. Connecting does not migrate existing sessions.
- **Desktop technology.** The VS Code desktop app is Electron, which is a packaging question separate from agent parity.

Disposition for this row: a candidate to evaluate, not a match or a recommendation.
