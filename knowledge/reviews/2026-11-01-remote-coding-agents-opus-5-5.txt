# Independent review: the Cogpit v3.5.3 proposal for remote Claude Code, Codex and Copilot sessions

**Reviewer:** GitHub Copilot CLI (claude-opus-5.5), read-only. Nothing was installed, edited, logged in, committed, published or started.

**What was inspected:** Cogpit release tag `v3.5.3` (annotated tag object `4a4c466b…`), which resolves to commit `f492f811adb4fa9e71aadf4954f8745034eeb3e8` in the local clone. All file:line references below are to that commit.

**Evidence labels:**
- **[OBS]** — I read it in the code.
- **[DOC]** — upstream documentation says it.
- **[INF]** — my inference.
- **[UNK]** — unknown.

---

## 1. Verdict: run a gated pilot only; do not adopt

Treat Cogpit v3.5.3 as a **gated, single-server, Copilot-only pilot**. Do not adopt it, and do not record it as an accepted decision.

**Why it is worth piloting:**
- For Copilot specifically, it is the deepest integration among the candidates I examined. It drives Copilot's own headless JSON-RPC server (the same engine the official SDK uses).
- It handles native approvals, user questions, exit-from-plan-mode, rewind, fork and model switching.
- It reads native `~/.copilot/session-state` history.
- Sessions it starts are owned by the host and survive client disconnects.

**Why it cannot be adopted as proposed:**
1. **It cannot join a process that is already running.** Cogpit can only import and resume a session from disk. It actively refuses sessions that another process holds (copilotTransport.ts:539-593). Arbitrary takeover is not available, which the owner suspected. The only verified way to steer the same running process is each vendor's own Remote Control, which goes through the vendor's cloud, not privately over Tailscale.
2. **Sessions are host-owned only while Cogpit's process lives.** One shared `copilot --headless --stdio` child serves every Copilot session on the host.
   - If that child crashes, every Copilot session on the host is dropped.
   - Restarting or upgrading Cogpit destroys live sessions and ends in-flight turns.
3. **It changes the native agent configuration it promises to preserve.** On every start it writes four skills into `~/.copilot/skills`, `~/.claude/skills` and `~/.codex/skills`. Those skills also apply to sessions started in a terminal.
4. **Its security defaults conflict with the proposal's assumptions:**
   - Any process on the server connecting over loopback skips authentication.
   - New sessions default to full access.
   - Hub device passwords are stored as plaintext JSON.
   - The Mac app is unsigned, partly built from private source, and silently stages and installs updates on quit. That defeats the "v3.5.3" pin.
5. **The install steps were not grounded in evidence.** The proposed steps assume systemd plus `loginctl` linger, glibc and a working native toolchain on a server whose distro is unknown. They pin neither the Copilot install nor one of the two Bun installs.
6. **Electron is not native macOS.** This is a distribution and integration gap. It is separate from agent parity and is not yet an accepted trade-off.

The owner's requirements take precedence. The no-terminal-UI, native-feature-parity and private-access requirements are met only partially and conditionally. The pilot's job is to measure that gap.

## 2. Findings, ranked by severity

### Critical (each one blocks the pilot until verified)

**C1. Live process identity: resume only, no join, and restarts are destructive.**
- [OBS] One child process serves all Copilot sessions: `copilot --headless --no-auto-update --stdio` (copilotTransport.ts:249; copilotRuntime.ts:35-44).
- [OBS] If the child crashes or its pipe closes, `discardTransport` clears every active session (copilotTransport.ts:1347-1380).
- [OBS] A normal shutdown sends `session.destroy` for each session, then `runtime.shutdown` (copilotTransport.ts:1382-1420).
- [DOC] On restart, unsent work is held and in-flight work is marked `unknown` (docs/orchestration.md:21-22).
- [OBS] Resume calls `sessions.checkInUse` and refuses sessions held by another process (copilotTransport.ts:539-593). External `copilot --resume` processes are detected by their command-line arguments (agent-descriptors.ts:951-955).
- [OBS] Copilot 1.0.105 on this review host writes `session-state/<uuid>/{events.jsonl, session.db, inuse.<pid>.lock, workspace.yaml}`. The file layout Cogpit expects therefore exists. Compatibility of the event schema is [UNK].
- **Consequence:** "survives laptop closure" is plausible. "Survives a service restart, upgrade or Copilot crash" is false for turns that are in progress.

**C2. Authentication depends on forwarding headers, and loopback is trusted.**
- [OBS] A request from a loopback socket with `Host` set to localhost, 127.0.0.1 or [::1] and **no** `Forwarded` or `X-Forwarded-*` headers skips authentication (server/security.ts:19-78).
- [INF] Two consequences follow:
  - Any other Unix user or local process on the server gets unauthenticated control of an agent running as the owner. Combined with the full-access default, that is equivalent to a shell as the owner.
  - Remote requests are authenticated only because Tailscale Serve adds `X-Forwarded-*` headers. If Serve forwarded without those headers, the whole tailnet would be unauthenticated.
- [UNK] I did not inspect Serve's exact header behaviour in Tailscale source. **Gate:** an unauthenticated request through the Serve URL must be rejected, and the number of local users on the server must be known.

### High

**H1. Native agent homes are modified.**
- [OBS] Every server start runs `installBundledSkills` (app-server.ts:188 → sessionCli/install.ts:140-147 → agents/skills.ts:29-46).
  - It writes the `cogpit`, `cogpit-browser`, `cogpit-sessions` and `cogpit-memory` skills into each existing agent home.
  - It follows symlinks (`realpathSync`, skills.ts:16), so a skills directory managed from a dotfiles repo would be written through.
  - It also installs launchers into `~/.cogpit/bin`.
- [OBS] The skill text promotes child sessions that default to `bypassPermissions`, `bun install --global cogpit-memory`, and transferring env files between devices (agents/bundledSkills.ts:4-15). It also contains environment details specific to the maintainer.
- [OBS] Cogpit separately appends its skill text to the Copilot system message (copilotTransport.ts:111-116, 515-516).
- [OBS, undocumented] Mitigation: set `COGPIT_SKILL_HOME` to a directory that does not exist. Injection is then skipped, because skills.ts:9-10 uses that directory as the root and line 34 skips when the root is missing. The appended system-message text remains.

**H2. Full access is the default.**
- [DOC] Full access is the default permission mode (docs/usage.md:42).
- [OBS] Both `bypassPermissions` and `auto` map to Copilot's allow-all, and `auto` also maps to autopilot (copilotRuntime.ts:104-112).
- The proposal's "full access *may* be default" understates this.

**H3. The Mac client and its supply chain.**
- [OBS] The DMG is built with `CSC_IDENTITY_AUTO_DISCOVERY=false`, so it is not Developer-ID signed or notarized (release.yml:175-183).
- [OBS] Release builds check out the private `editions/team` submodule with a deploy key and expect it to be present (release.yml:143-145, 182; .gitmodules). The published binary is therefore not reproducible from public source.
- [OBS] The updater:
  - checks about 5 seconds after launch and periodically, then stages the newest release;
  - installs it on any quit;
  - verifies only a SHA-512 from the release's own manifest, with no codesign check (electron/updater.ts:91-162; updateFeed.ts:48-59).
- The only overrides are dismissing a specific version or setting `COGPIT_UPDATE_FEED_URL`.
- [DOC] Contradiction: docs/development.md:48 says public macOS auto-updates "require the signed release setup".
- [DOC] The release `v3.5.3` was published 2026-10-30 with `"immutable": false`.
- **Effect:** the Mac pin is not durable, and version skew between the hub and the servers is likely.

**H4. Credentials at rest.**
- [OBS] The hub registry stores device passwords in plaintext JSON (`devices.local.json`, mode 0600), not in the Keychain (server/hub/registry.ts:6-39, 104-128).
- [INF] In the proposed phone topology, one server holds every other server's password. Compromising that one account gives access to all of them.

**H5. Copilot feature coverage is narrower than "preserve native capabilities".**
- [OBS] Copilot descriptor (agent-descriptors.ts:893-1017):
  - Disabled: `mcp`, `slashCommands`, `workflows`, `goals`, `subagentTranscripts`, `imageInput`, `tokenStreaming`.
  - Not set: `agentsDir`, `commandsDir`, `pluginsDir`.
  - Enabled: `nativeRewind`, `nativeFork`, `undo`, `midTurnSteering`.
- [OBS] Session defaults (copilotTransport.ts:267-279):
  - `requestElicitation:false`, so MCP elicitation forms never reach the UI.
  - `includeSubAgentStreamingEvents:false`.
  - `hooks:false` — [INF] this is the SDK callback-hook flag, not user hooks; [UNK] whether user hooks still run.
  - `enableConfigDiscovery:true`.
- [OBS] The complete Copilot RPC surface Cogpit uses: models, quota, usage, create/resume/send/delete, fork, rewind preview and rewind, permission modes, model switch and effort, pending permissions, abort, destroy and shutdown (copilotTransport.ts:420-1411).
  - It never selects a custom agent and never manages MCP.
- [OBS] The settings editor targets `config.json` (agent-descriptors.ts:962).
  - [DOC] The Copilot CLI 1.0.93 changelog says user settings are read only from `~/.copilot/settings.json`. Cogpit edits a file the CLI ignores.
- [DOC] Copilot 1.0.101: headless/SDK sessions without an OAuth handler skip MCP servers whose saved tokens require sign-in.
- [DOC] Copilot goals, workflows and MCP editing are not exposed (usage.md:22). Copilot session sharing is rejected (self-hosting.md:176).

**H6. Bootstrapping on an unknown Linux server.**
- [OBS] The root `postinstall` runs `electron-builder install-app-deps` (package.json). On a headless server, `bun install` will therefore:
  - download Electron;
  - prepare native modules for Electron's ABI, including node-pty.
- [INF] On musl, or without prebuilt binaries, that needs python3, make and a C++ toolchain.
- [OBS] At runtime under Bun, the server uses `Bun.Terminal` (pty-backend.ts:47-67) but still imports `node-pty` statically.
- [DOC] The upstream sample is a **system** unit with `LoadCredential` (self-hosting.md:208-229). The user unit plus linger was the prior agent's own untested adaptation, and no non-systemd procedure was given.
- [UNK] Whether Copilot's OAuth token, stored at `/login` in a keyring or plaintext, is readable from the service's non-interactive environment.

### Medium

**M1. Protocol coupling to the Copilot version.**
- [OBS] The handshake requires `protocolVersion === 3` exactly (copilotTransport.ts:245, 982-990).
- [DOC] The official SDK instead accepts any version ≥ 3.
- [INF] Copilot 1.0.105 speaks protocol v3. That has been in the SDK since commit `1653812a` (2026-03-07), and SDK main pins CLI `1.0.106-2`.
- [INF] Interactive `copilot` updates itself by default. Only Cogpit's child gets `--no-auto-update`. A future v4 would break Cogpit after its next restart.
- [OBS] Cogpit also offers user-triggered CLI updates through `server/routes/provider-updates.ts:44`.

**M2. The empty-Mac workaround is valid but unnecessary.**
- [OBS] `App.tsx:1053-1054` shows `SetupScreen` when there is no Claude data directory, and `SetupScreen.tsx` has no add-device path.
- [OBS] `detectBootstrapConfig` accepts either an install marker (`~/.copilot/session-state` or `~/.codex/sessions`) or a codex/copilot binary on the login-shell PATH (config.ts:222-242; electron/main.ts:12-18).
- Installing the Homebrew cask works, but either of these is lighter:
  - an empty `~/.copilot/session-state` directory;
  - pointing the field at any directory containing `projects/` (config.ts:341-366).
- Installing the binary also invites accidental local sessions, which contradicts "always remote".
- [INF] Any of these creates `~/.copilot` on the Mac, and the Mac's embedded server will then inject skills there (H1).

**M3. Supply-chain pinning gaps in the proposed commands.**
- The Copilot installer, `curl … | bash`, was not given `VERSION=`.
- The Cogpit tag is mutable. The clone should be verified against the commit `f492f811`.
- `packages/cogpit-memory` has its own `bun.lock`, but the proposal installs it without `--frozen-lockfile`.
- The Bun installer is version-pinned but not checksummed.
- The "Node.js 22+" prerequisite is unexplained.

**M4. Multi-host.**
- [DOC] The UI shows one device at a time (usage.md:109). There is no merged session list.
- [DOC] Browser sessions expire after 30 minutes idle or 8 hours total, and require HTTPS because the cookie is `Secure` (self-hosting.md:179, 285-312). Expect frequent re-logins on the phone.

**M5. Tailscale Serve route preservation.**
- [INF] Serve configuration covers the whole node.
- **Rollback** must be `tailscale serve --https=8443 off`, never `reset`.
- [DOC, per Tailscale; not re-fetched here] Enabling HTTPS certificates publishes node names in public Certificate Transparency logs. Account for this in the privacy requirement.

### Low

- **L1. Repository hygiene.** [OBS] The public tree ships the maintainer's `.claude/deployments-logs.md` with infrastructure identifiers (not reproduced here). Line 27 states that "installed parity remains unverified". This signals a fast-moving project developed largely by an agent.
- **L2. Terminal panels exist.** [OBS] Cogpit includes node-pty/xterm panels. Chat is the primary surface, so this is acceptable only if no pilot step needs the terminal.
- **L3. Claude path.** [OBS] Cogpit uses Claude Agent SDK 0.3.306. It forces `autoCompactEnabled:true` in a layer that outranks user settings, and injects a browser plugin, hooks and environment changes (sdk-session.ts:379-478, 449-453; agentEnv.ts:38-62). User, project and local settings still load because `settingSources` is omitted ([DOC] SDK default).

## 5. First-server Copilot pilot (not executed)

### Phase 0: facts needed before any copy/paste install commands

Collect these with read-only commands only, and keep the results unpublished:
- **OS and libc:** `/etc/os-release`, `uname -m`, `ldd --version 2>&1 | head -1`.
- **Init system:** PID 1 (`ps -p 1 -o comm=`), whether `systemctl --user` works, and whether linger is permitted or needs sudo.
- **Accounts:** the account name and home directory, and how many interactive local users exist (this decides whether C2 is acceptable).
- **Copilot:** `copilot --version` (must be 1.0.105), whether the auth token lives in a keyring or in plaintext, and the auto-update setting.
- **Existing agent state:** whether `~/.copilot/{settings.json,config.json,skills,agents,hooks,mcp-config.json}` exist (names only). Whether `~/.claude` and `~/.codex` exist, and whether any of their skills directories are symlinked.
- **Toolchain:** git, curl, unzip, gcc/g++, make, python3, and disk and RAM for an Electron-heavy `bun install`.
- **Tailscale:** `tailscale version` and `tailscale serve status` (which ports are taken; whether HTTPS certificates are enabled for the tailnet).

### Gates

Each gate must pass before moving to the next. Failing any gate means rollback.

| Gate | Pass criterion |
|---|---|
| G0 | Backups exist (mode 0600, outside Git) of `~/.copilot`, plus `~/.claude/skills` and `~/.codex/skills` if present. Phase 0 answered. |
| G1 | The clone's `v3.5.3` resolves to `f492f811…`. Bun is exactly 1.3.14. `--frozen-lockfile` is used in **both** packages. Copilot installed with `VERSION=v1.0.105` or already present and left untouched. Copilot auto-update disabled for the account. |
| G2 | Service runs with `COGPIT_HOST=127.0.0.1`, a password file, and `COGPIT_SKILL_HOME` set to a directory that does not exist. After start, no `cogpit*` skills appear in any agent home. |
| G3 | Through the Serve URL from another tailnet device, an authenticated endpoint returns 401 without credentials. If other local users exist: **fail**, unless the host is dedicated. |
| G4 | Mac: unsigned-app Gatekeeper override is an explicit owner decision. The empty-marker gate is used instead of the cask. Updater dismissed or feed overridden, and the version still shows 3.5.3 after quitting and relaunching. |
| G5 | Parity. Every check is compared with a terminal session in the same repo: Opus 5.5 listed and selectable; an approval prompt appears in a non-full-access mode; ask-user and exit-plan-mode flows; a canary instruction in `AGENTS.md` / `.github/copilot-instructions.md`; a canary user skill; a canary stdio MCP server (no OAuth); a canary user hook writing a marker file; custom-agent availability; rewind; fork. |
| G6 | Continuity: start a long turn, Cmd-Q the Mac app, close the lid for 10 minutes, reopen. The turn has continued and its output is present. |
| G7 | Phone with the Mac **powered off**: open the server URL, log in, see the same session, send a message, approve a tool. |
| G8 | Restart mid-turn: the documented `unknown` state appears, and resume works afterwards. `copilot --resume <id>` still works from a terminal on the server. |
| G9 | Discovery: a pre-existing terminal session is listed and resumable. While it is still running in the terminal, Cogpit refuses it. Record this as "import, not takeover". |
| G10 | After 7 days: Copilot and Cogpit versions unchanged, and no unexpected writes in the agent homes (compare the file lists). |

### Rollback

1. Stop and disable the service. Remove linger if it was added only for this pilot.
2. Run `tailscale serve --https=8443 off`. Do **not** run `reset`.
3. Remove the app directory, `~/.cogpit` and the Cogpit data directory (default `~/.config/cogpit`, self-hosting.md:192).
4. Remove any `cogpit*` skill directories and restore the backups.
5. On the Mac: delete the app, its application-support data and the marker directory.

Copilot sessions created during the pilot stay in native session state and remain resumable from the terminal.

## 7. Sources, revisions and limits

**Sources inspected:**
- **Cogpit:** github.com/gentritbiba/cogpit, tag `v3.5.3` → `f492f811adb4fa9e71aadf4954f8745034eeb3e8` (local clone). The GitHub API reports the latest release as v3.5.3, published 2026-10-30, `immutable:false`.
- **Copilot SDK:** github.com/github/copilot-sdk `main` (protocol v3 since `1653812a`; `cliVersion 1.0.106-2`).
- **Copilot CLI:** github.com/github/copilot-cli `main`, changelog through 1.0.105, README, install script (`VERSION=`), and GitHub's documentation on remote-steering Copilot CLI.
- **Claude:** docs.anthropic.com / code.claude.com pages on Remote Control and Agent SDK `settingSources`.
- **Paseo:** github.com/getpaseo/paseo — README, providers and connectivity docs, releases v0.14.0 and v0.15.0-beta.1.
- **Happier:** github.com/happier-dev/happier (`dev`) — README and docs on continuing a session, capabilities and Copilot; releases.
- **HAPI:** github.com/tiann/hapi `main` — README, agents.md, how-it-works.md.
- **OpenCode:** github.com/anomalyco/opencode — README.

**Limits:**
- No runtime tests of any kind.
- Tailscale Serve header behaviour was not verified against Tailscale source.
- Source code for Paseo, Happier and HAPI was not inspected (documentation only). Their commit SHAs were not recorded.
- Codex remote-control options were not verified.
- GitHub code search requires a login, so it was not used.

**Assessment of the earlier agent.** I found no fabrication: the release, the environment variables (self-hosting.md:190-202), the port and the documented Copilot limits are all real. However, it overclaimed and under-disclosed:
- It presented "starts and resumes all three agents" and "approvals" as working fact. They exist in the code but have never been tested at runtime.
- It hedged "full access *may* be default". The docs state that it is the default.
- It proposed the cask workaround without noting that it is unnecessary, or that `SetupScreen` has no add-device path.
- It presented a self-invented systemd user unit plus linger as if it were the upstream method.
- It left the Copilot install and the `cogpit-memory` install unpinned.
- It treated "close and reopen the app" as proof of continuity, which tests history rather than a live process.
- It missed the skill injection, the loopback bypass, the destructive restart behaviour, the auto-updater, the private build input, the plaintext hub credentials and the stale `config.json` settings path.
